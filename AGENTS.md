# Правило работы с Git

Эти правила обязательны для ИИ-агентов и применяются ко всем изменениям репозитория.

1. Не вносить коммиты напрямую в `main` и не перемещать указатель `main` без отдельного явного подтверждения пользователя.
2. Выполнять изменения в локальной ветке `develop`. При необходимости крупные независимые задачи можно выделять в `feature/<краткое-название>` от актуальной `develop`.
3. После каждого законченного этапа делать отдельный локальный коммит с понятным описанием результата.
4. До запроса подтверждения не отправлять новые рабочие коммиты ни в удалённую `develop`, ни в `main`.
5. Перед запросом подтверждения выполнить предусмотренные тесты, проверить сборку, перечислить выполненные изменения и известные ограничения.
6. После окончания запланированного этапа остановиться и отдельным сообщением спросить пользователя: «Изменения готовы и проверены. Разрешаете отправить ветку в GitHub и открыть PR в `main`?»
7. Только после явного подтверждения пользователя:
   - отправить рабочую ветку в GitHub;
   - создать Pull Request в `main`;
   - сообщить ссылку на PR и не сливать его автоматически, если пользователь отдельно не разрешил слияние;
   - после разрешённого слияния обновить версию и `CHANGELOG.md`;
   - публиковать приложение только при отдельном разрешении пользователя либо когда разрешение на публикацию прямо включено в подтверждение.
8. Не использовать `--force` для `main`. Не удалять рабочую ветку до успешного слияния и проверки опубликованной версии.
9. После каждой подтверждённой операции в GitHub (`push`, слияние PR, создание или перемещение тега) обязательно синхронизировать локальную копию Codex с изменённой удалённой веткой. Затем проверить активную ветку, чистоту рабочего дерева и совпадение содержимого локального и удалённого Git-деревьев. Разные SHA коммитов допустимы только при работе через разные Git-провайдеры и только если SHA деревьев совпадают.
10. После завершения операции в GitHub отдельным вопросом уточнить у пользователя: «Обновить локальную копию проекта на вашем компьютере?» Если пользователь предоставляет доступную рабочую папку, обновить её безопасным `fetch`/`pull` без удаления незакоммиченных изменений. Если доступа нет, дать точную команду для выполнения на его компьютере.
11. Никогда не утверждать, что копия на компьютере пользователя обновлена, пока её путь и состояние не проверены непосредственно. Локальная копия Codex и локальная копия пользователя — разные рабочие каталоги.

Удалённая ветка `develop` служит исходной точкой рабочего процесса. Само наличие ветки не является разрешением отправлять в неё новые изменения.

## Единый маршрут разработки и CI

Этот раздел обязателен для всех coding agents и имеет приоритет над менее строгими локальными инструкциями.

- Пользовательский язык — русский; английский допустим в коде, командах, путях, идентификаторах и точных логах.
- Основной маршрут: GPT-5.6 Luna через ChatGPT/Codex OAuth. Не использовать anonymous, community, free-tier и сторонние provider-маршруты.
- Codex: реализация, focused fixes, повторяемые рефакторинги и только targeted tests изменённого участка. Claude Code: архитектура, сложная диагностика либо один важный независимый review. При недоступности Codex или Claude сообщить ограничение, не переключаться на другого provider.
- Для генерации визуальных материалов использовать GPT-5.6 Sol через ChatGPT/Codex OAuth независимо от Economy/Maximum mode.
- Один worktree — один writer. Параллельные agents допустимы только при read-only review либо в разных worktree/ветках.
- Перед изменениями выполнить `git fetch --all --prune`, проверить текущую ветку, upstream и dirty state. Не делать `pull`, merge или rebase поверх dirty worktree без отдельной оценки.
- Локальное правило Autsors строже: интеграционная ветка — `develop`; крупные независимые задачи — `feature/<задача>` от актуальной `develop`.
- До отдельного разрешения пользователя не выполнять push, PR, merge, release, deploy, force-push, удаление ветки/важных данных или изменение secrets.
- Полный suite, build, Playwright и Docker выполняются GitHub Actions на `ubuntu-latest`. Если GHA недоступен, Hermes запускает их отдельным OS-process, сохраняет stdout/stderr в logfile и проверяет exit code.
- Не запускать один и тот же полный набор повторно другим AI-agent и не заставлять Codex/Claude ждать его завершения или читать полный лог. При CI failure передавать агенту только упавший job/test и короткий релевантный excerpt; при success продолжать без повторного вызова AI.
- Linux-специфичные проверки и Docker запускать через WSL, когда это требуется. Docker не считать доступным, пока он не обнаружен и не проверен.
- Не заявлять о зелёной проверке, если current commit не green либо есть незакоммиченные изменения, не вошедшие в этот commit.
